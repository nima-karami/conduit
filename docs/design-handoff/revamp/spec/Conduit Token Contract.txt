Conduit — token contract
What Claude Code needs to replace the six shipped themes with three — including the syntax palette, now per-theme per your call on (b). Rows marked EXISTS TODAY are already in styles.css under [data-theme]; the six existing blocks are deleted and these three replace them. Rows marked NEW AXIS do not exist in any form — today --r: 9px and --r-sm: 6px are global and no theme overrides them, which is precisely why Aero and Neon are not expressible as themes yet. Values are lifted from the built frames in Conduit Design Language, not invented here.
Colour
EXISTS TODAY
The six deleted themes already overrode exactly these, so the mechanism is proven — only the value sets change. Validation rule: every text tier must clear 4.5:1 against the lightest surface it can render on, not the ground — in the rebuilt language that means Aero: the #ffffff card on the rgba(255,255,255,.74) panel over the #eceff4 ground; Neon: the #0c0a16 field on the #0a0812 panel. Code text is measured on the ink panel instead (#1b1e2b / #06050c). Where a tier cannot clear its own lightest surface, promote the element to --text-dim rather than lifting the tier. Code surfaces are dark in every theme — so the diff-tint problem does not exist. An earlier revision of this contract set --code-base #fbfbfd for Aero Light and then re-derived --syn-*, --ok and --warn against light add/delete washes. That was wrong: 5a puts the terminal on #1b1e2b at 20px radius inside light Aero, and styles.css says code surfaces stay dark by design. Both agree, so the editor and diff panels are ink in Aero and #06050c in Neon, and the whole light-syntax palette — #fbfbfd, #5c6274, #9d4718, #177049, #8a5f0f — is withdrawn. Use the language’s on-ink values: body #d3d7e4, comments and gutter #6f748a, strings #7fd6a4, identifiers #9db4f0, keywords #a56be8; UI semantics --ok #2f8f5b, --bad #c4483f, and warn as the fill/text pair #d6922a / #9a7530 on #fff8ec. Accepted, with the numbers on record: on ink --syn-comment #6f748a measures 3.58:1 (3.91 in Aero Dark), white-on-#d6922a on the primary amber button 2.62:1, and --syn-keyword #a56be8 4.11:1 on the current-line row. These are the Design Language’s own values and are signed off as-is — they are editorial choices about a dense pro tool, not oversights. Do not "fix" them during implementation; if the bar changes later, change it in the language and let it flow down here. Do not dim them further with opacity — an opacity multiplier on top of an already-marginal tier is how a 3.5:1 value becomes a 2:1 one, and the gutter is the wrong place to save contrast. Note that Neon reassigns --amber from amber to magenta: attention keeps its semantic slot and changes hue, which is the whole reason to name tokens by role rather than colour.

Density — the axis this contract nearly broke
READ FIRST
styles.css already drives every height, padding and gap from ~28 --density-* tokens, with a full :root[data-density="compact"] override set. Base font size is calc(var(--density-font) * var(--font-scale)) — density sets the base, the Font size setting scales it, and the two compose deliberately.
Every pixel value in the screen designs is a hard-coded literal at Comfortable density. Handing those numbers over as-is would replace a working two-mode spacing system with one fixed mode, and Compact would silently stop working.
The rule for anyone implementing these designs
The new axes in this contract are shape and material — radius, hairline, elevation, glow, notch. Those are theme-scoped and density-independent. Spacing and size stay with density. Where a design shows a padding or a height, read it as the Comfortable value of an existing --density-* token, not as a new constant. Two selectors, two jobs:
/* theme: shape + material only — never spacing */
:root[data-theme="neon"] { --r-panel: 0; --r-card: 0; --hair: #2a2145; --glow: 0 0 26px rgba(0,240,255,.14); }
/* density: spacing + size only — never colour or radius */
:root[data-density="compact"] { --density-tabbar-h: 32px; --density-row-pad-v: 4px; }
Resolved: the chrome bands are density-owned, and theme must not change their height. Earlier revisions had Aero at 40px and Neon at 36px, with tab rows at 34 and 30 — theme silently driving spacing, which the split above forbids. All three bands now take one value per density: topbar 40px / 34px, centre tab row 34px / 28px, right-rail tabs 40px / 32px (Comfortable / Compact). Neon differs by material only — flush hairline instead of a floating pill.
:root { --density-topbar-h: 40px; --density-tabbar-h: 34px; --density-rtab-h: 40px; }
:root[data-density="compact"] { --density-topbar-h: 34px; --density-tabbar-h: 28px; --density-rtab-h: 32px; }
Note --density-rtab-h is new; the right rail currently reuses --density-tabbar-h, which couples two bands that want different heights. Still open: the notch is a fixed 14px clip-path inset, so at Compact it eats proportionally more of a shorter card — scale it with density or cap it on short surfaces. The sessions-panel header is also still theme-varying (Aero pads, Neon uses a fixed 26px band); fold it into the same treatment when implementing.

Resolved — themes and fonts are coupled, and the picker still wins. Each theme carries a default UI + mono pair. Switching theme applies that pair; the user may then override either picker, and the override sticks. So ThemeDef gains its defaults and the theme-change handler writes them unless the user has set that axis explicitly — which needs one flag per axis so a deliberate choice is not clobbered by the next theme switch.
export interface ThemeDef {
id: string; label: string;
swatch: [string, string, string];
shape: 'round' | 'sharp';
/** Applied on theme switch unless the user has overridden that axis. */
fontUi: string; // font id from UI_FONTS
fontMono: string; // font id from MONO_FONTS
}
// aero / aero-dark → { fontUi: 'figtree', fontMono: 'plexmono' }
// neon → { fontUi: 'chakra', fontMono: 'jetbrains' }
// AppSettings gains two flags, both default false:
// fontUiPinned: boolean; fontMonoPinned: boolean
// setTheme(id): if (!s.fontUiPinned) s.fontUi = THEME.fontUi;
// if (!s.fontMonoPinned) s.fontMono = THEME.fontMono;
// user picks a font → set the matching *Pinned flag true
Without the pinned flags this is lossy in one direction or the other: write always and a chosen font is destroyed on the next theme switch; write never and Neon renders in Hanken Grotesk for every existing user. Existing installs have no flags set, so they inherit their theme’s pair on first launch — which is the intended migration.
