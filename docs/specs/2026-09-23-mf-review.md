# Feature Spec: Review grouped by repo (multi-folder 12a)

**Tier:** FULL   **Feature type:** UI
**Mode:** autonomous. Would-be questions are recorded in §13 with the pick taken.
**One-line request:** mf-review: add a leading `All repos ▼` chip to the Review header. With All
repos selected, the source is locked to Working tree, and picking a commit or compare first narrows
to one repo. Diffs and the navigator are grouped by repo with reviewed counts. Progress is keyed by
repo root.

**Builds on:** `.autoloop/locked.md` (L3 `repoRoot` on git messages, L4 `RepoInfo.tag`, L7 review
notes and marks stay per repo root) · mf-changes (`docs/specs/2026-09-23-mf-changes.md` §3: `RepoChanges`,
`project.repoChanges`, `GitActionIntent.repoRoot`, `HunkActionHost.rootFor`; §3.1 lists exactly
what is consumed and what this item adds) · archived
`docs/specs/archive/2026-09-05-review-mode.md` (the header, navigator and action bar this extends)
· `2026-08-31-review-fidelity.md` T1 (view-state memory, re-keyed here). Design:
`.autoloop/handoff/README.md` §12a, `screenshots/12a-review.png`, `Conduit Multi-Folder
Flows.dc.html` `#12a`.

## 1. Problem frame

- **Job:** a session now spans several git repos (home, nested, attached). The user wants to review
  everything the agent changed across all of them in one pass, keep a separate reviewed count per
  repo, and still drill into one repo's commit or comparison.
- **Actors:** the reviewer (keyboard and pointer), and the agent that receives the notes handoff.
- **Success outcomes:**
  1. One Review tab lists every repo's working-tree changes, grouped by repo in the Changes tab's order.
  2. Every mark and note lands on the repo that owns the file. Two repos that change the same
     relative path (`package.json`) never share a card, mark, fold, DOM node or scroll anchor.
  3. A commit or comparison review is always about exactly one repo, and the UI says which.
  4. **A single-repo session looks and behaves exactly as it does today:** no chip, no group
     headers, and the handoff produces the same bytes.
- **Non-goals:** merged cross-repo history (12b forbids it); a cross-repo compare; collapsible or
  sticky group headers; per-group menus; changing where marks and notes are stored; the session
  card's review diffstat (it stays the active repo's git-status count, §13 D10).

## 2. Behavior & states

### 2.1 Repo scope is carried by `ReviewSource`, not by separate state

```ts
type ReviewSource =
  | { kind: 'working'; scope?: ReviewScope; repoRoot?: string }          // absent repoRoot ⇒ All repos
  | { kind: 'commit'; sha: string; subject?: string; repoRoot?: string } // shape unchanged
  | { kind: 'range'; base: RefEndpoint; head: RefEndpoint; repoRoot?: string }; // repoRoot is new
```

- **`reviewRepos`** = the active session's present detected repos (missing folders are already
  excluded per L9), in mf-changes' display order. The chip is **visible iff
  `reviewRepos.length >= 2`**.
- **`resolveReviewRepo(source, reviewRepos, fallbackRoot)`** (pure, new):
  - working without `repoRoot` + chip visible → **All repos** (`null`).
  - working without `repoRoot` + chip hidden → the single repo, else `gitRootForSession(active)`.
    This is today's behavior.
  - working with a `repoRoot` in `reviewRepos` (matched with `normalizeRoot`) → that repo.
  - working with a `repoRoot` **not** in `reviewRepos` → All repos (§4 "repo leaves").
  - commit or range with any `repoRoot` → that root, **even when it is outside `reviewRepos`**.
    A terminal sha link resolves to the terminal's cwd repo, which the host has validated
    (`validateCommitsResult.root`). Today's link-cwd behavior must survive. The chip then shows
    that root's basename.
- **S1:** every commit or range source carries a `repoRoot` once it is set. `openReviewForCommit`,
  the picker, `CompareDialog` and the blame lens stamp the narrowed repo, the caller's `repoRoot`, or
  `gitRootForSession(active)`.
- **S2:** every builder of a new working source keeps the current `repoRoot`. That covers the scope
  segment (`ReviewSourceControl.setScope`), the compact `···` scope rows and the picker's
  `Working tree` row. App `setReviewSource` / `openReviewScoped` / `openReviewForCommit` pass
  `repoRoot` through. Today all of them drop it (measured by the reviewer: app.tsx:691–701,
  review-source-control.tsx:29–33, review-view.tsx:1683, commit-picker-menu.tsx:206).
- **Global entry points reset narrowing:** `Mod+Shift+R`, the palette, the session card and the
  Changes tab's Review button open working with no `repoRoot`, which is All repos. This is
  intentional.

### 2.2 Primary flow

1. The user opens Review. The header reads: panel toggle · **`[folder] All repos ▼`** ·
   `Working tree ▼` (locked) · `All | Staged | Unstaged` · `n files · +a −d` · meter ·
   `x / y reviewed` · search · `···`.
2. The cards show a **group header** for each repo with ≥1 listed file, followed by its cards. The
   navigator shows the same groups with `reviewed/total`.
3. `J`/`K`, `m`, `o`, search, the file filter and note landing work over the concatenated list and
   cross group boundaries in list order.
4. **Narrow:** picking a repo in the chip yields `{kind:'working', scope, repoRoot}`. The scope is
   kept, the group headers go, only that repo is listed (today's look) and the source trigger
   unlocks.
5. **Commit or compare:** the picker lists the narrowed repo's commits. Picking one yields
   `{kind:'commit', sha, repoRoot}`. `Compare refs…` opens `CompareDialog` on that repo's refs and
   yields `{kind:'range', …, repoRoot}`.
6. **Back:** `All repos` in the chip yields `{kind:'working', scope}`, where the scope is kept if the
   previous source was working and is `all` otherwise. Picking a different repo while on a commit or
   range yields that repo's working tree.
7. Repo-specific entry points open already narrowed: a terminal sha link, History's "Review commit"
   (mf-changes passes the history chip's repo into the existing `onReviewCommit(sha, subject,
   repoRoot, sid)`), the blame lens (`repoForPath`), and a note glyph (§3.2, which lands on the file
   in All repos when the note's repo is in the set).

### 2.3 Header (extends review-mode §2.2)

| Element | All repos | Narrowed | Single-repo session |
|---|---|---|---|
| Repo chip | `IconFolder` `All repos` `IconChevronDown`, `title="Reviewing all N repos"` | glyph, repo name, caret; `title` = display path (§2.5) | **not rendered** |
| Source trigger | `Working tree`, **locked**: `aria-disabled="true"`, focusable, activation is a no-op; `title` and an sr-only `aria-describedby`: "All repos reviews the working tree. Pick one repo to review a commit or compare refs." | today | today |
| Scope segment | enabled; applies to every repo | today's rule | today |
| Stats, meter, count | totals over every listed file | that repo | today |

- **Chip menu** (existing `ContextMenu`, anchored like `···`): `All repos` (checked when active),
  separator, then one row per `reviewRepos` entry: name, `checked` on the current repo, and the
  hint `n files` in the current scope, `clean`, or `…` before `repoChanges` arrives. Clean
  repos stay pickable. A commit or range on an out-of-set root adds no menu row; the chip label alone
  shows it.
- **Compact header** (`useElementWidth(head) <= 480`, the existing breakpoint): the chip shows only
  glyph and caret, and its label moves to `aria-label` and `title`.

### 2.4 Card list grouping

- **Group header**, shown in All repos mode only: `IconFolder` · **name** (600) · a tag pill
  (`Home` accent / `Nested` warn / `Attached` neutral, reusing mf-changes' tag styling) · mono
  muted `branch · n files` · a flexible 1px rule. It carries `role="heading" aria-level="3"` and is
  not interactive. `n files` counts after scope and filter. With no branch, only `n files` shows.
- Groups follow `reviewRepos` order, files keep today's order inside a group, and **empty groups are
  omitted** from the cards and the navigator.
- **Windowing:** the window list becomes `items: (group | file)[]`. Group items have one fixed,
  unmeasured height. **Cursor, `pathIndex`, anchors and `scrollToFile` stay file-indexed**, and one
  `fileIndex → itemIndex` map converts them to window offsets, so `J`/`K`, restore and reveal
  cannot drift by the number of headers above them. Headers are keyed siblings of the cards (repo
  CLAUDE.md: virtualized rows are direct keyed children). A header scrolled out of the window
  unmounts, so screen-reader heading navigation only sees mounted groups; the navigator's group
  labels remain the complete outline.

### 2.5 Navigator grouping (extends review-mode §2.3)

- **Header summary:** in All repos mode, `N changes · M repos +a −d`, matching mf-changes' Changes
  header. Otherwise as today. Refresh calls the app's `refreshChanges`, which mf-changes makes
  refresh every repo. The filter's `N of M` counts across all groups.
- **Group label row:** mono name on the left, `reviewed/total` on the right (`room-message-bus
  1/2`), `aria-label="<name>, r of t reviewed"`. It is a fixed-height item in `ReviewFileNav`'s
  window and is skipped by row focus. Its `title` is the **display path**: `RepoChanges.sub` when
  present (`room-message-bus/vendor/proto-schemas`, the form 9c uses), else the root.
- Inside a group, `Staged` / `Changes` sub-labels appear only when the group has both. The
  per-section review icon is not shown in grouped mode, because the scope segment owns scope.
- Row hover actions (Stage / Unstage / Discard) carry the row's `repoRoot`.
- **Bulk kebab** in All repos mode: `Stage all` and `Unstage all` fan out (§2.6). `Stash`, `Pop` and
  `Discard all` are disabled with `title="Pick one repo first"`. Narrowed: today's menu, scoped to
  that repo.

### 2.6 Action bar (extends review-mode §2.4)

| Part | All repos | Narrowed / single |
|---|---|---|
| Notes | `N notes · M pending`, summed over every `reviewRepos` root | today |
| Handoff | pending notes from **every** `reviewRepos` root, including repos with no listed files (§3.3) | today, byte-identical |
| `Stage all` | fans out over every listed group; `title="Stage every changed file in N repos"` | today |
| `···` → `Discard all changes…` | disabled, `title="Pick one repo to discard its changes"` | confirm + discard of **that repo's** change list and count |

- **Reversible bulk ops fan out. Irreversible or per-repo-semantic ops (discard, stash, pop) need
  narrowing** (§13 D3).
- **Fan-out** lives in app.tsx next to `runGit`: `runGitFanOut(op, roots)`. It runs sequentially per
  root, calls `rereadOpenDiffs` per root, toasts `Git (<name>): <error>` and continues after a
  failure, and does one `refreshChanges()` at the end. `onGitAction` becomes
  `(intent) => Promise<void>`, so the triggering control can hold `disabled` + `aria-busy` until the
  promise settles. That also blocks a double click.

## 3. Data / interface contract

### 3.1 Consumed from mf-changes, and what this item adds

```ts
// consumed as-is (mf-changes §3)
interface RepoChanges { root; name; tag: 'home'|'nested'|'attached'; sub?; changes: ChangeDTO[] }
project.repoChanges?: RepoChanges[]        // one reply for all repos, display order
GitActionIntent = { op; path?; repoRoot? } // runGit uses repoRoot ?? gitRootForSession
HunkActionHost.rootFor(absPath)            // per-file root + that repo's staged/conflicted sets
git:history | git:refs { …, repoRoot? }    // mf-model L3, host-validated
// added by this item
GitActionIntent.repoRoots?: string[]       // fan-out (§2.6); exclusive with repoRoot
git:resolveRange | git:rangeDiff { …, repoRoot? }  // mf-changes §6 leaves these to mf-review
```

The host validates the added `repoRoot` fields the same way mf-model validates the others: omitted
means today's `gitRoot(session)`, and an unknown root gets the failure shape and never runs git.
Until `repoChanges` arrives, Review shows today's whole-list loading state, because mf-changes sends
one reply for all repos. **A failing `git status` reads as clean** in mf-changes' MVP (its D11), so
this item has no per-group error state (§13 D1).

### 3.2 Review-internal contract

- **`ReviewFile = ChangeDTO & { repoRoot: string }`.** `ReviewView` takes `repos: RepoChanges[]`
  in place of `changes` + `changesRoot`. Commit and range loaders tag their files with the source's
  `repoRoot`.
- **K1, file identity:** everywhere inside ReviewView, the review-nav store and the view-state
  memory (every key listed in §2.7), a file's key is its **absolute path**, in every mode, on one
  code path. Card DOM keeps `data-path` = relative path (so existing e2e selectors hold) and **adds
  `data-root` = normalized root**. Internal DOM lookups match both attributes.
  `ReviewNavModel.reviewed` holds absolute paths, and `onPick` / `onToggleReviewed` take a
  `ReviewFile`.
- **K2, stores unchanged:** marks use `setReviewMark(normRoot(file.repoRoot), {source: sourceKey,
  path: file.path, …})`, and notes use `patchNotes(normRoot(file.repoRoot), …)`. Formats, `sourceKey`
  strings and caps are unchanged, so every existing mark and note still applies.
- **K3, view key:** `viewKey = sourceKey + '\0' + (resolvedRoot ?? '*')` drives `adoptReviewSource`,
  the scroll/focus reset, the source announcement and card keys. **Marks keep the bare
  `sourceKey`.** A chip change therefore resets scroll and focus like a source change, while marks
  made in All repos stay valid when narrowed and the reverse.
- **`groupReviewFiles(files, repos, reviewed, repoGit) → ReviewGroup[]`** (pure): `{root, name, tag,
  sub?, branch?, files, reviewed}`, in repos order, `branch` read from the live `session.repoGit`, with empty groups dropped. `reviewedPaths` /
  `staleMarks` run per group, and the header total is their sum. `NOTES_ARTIFACT_PATH` is excluded
  per group.
- **Hunk ops:** these use mf-changes' `HunkActionHost.rootFor(absPath)`, so Review passes only the
  absolute path. Card `stagedSide` / `conflictedSide` are keyed by absolute path.
- **Notes:** app.tsx calls `loadNotesFor` for every `reviewRepos` root, not only the active one, so
  editor glyphs work in every repo. `NoteTarget` gains `root`. ReviewView lands on
  `joinPath(root, path)`, and a note whose root is not in the current view leaves the list where it
  is (today's "not in this changeset" rule). `canAddNote` / `refusedMessage` are evaluated per card
  repo.
- **Plumbing:** `CommitPickerMenu` and `CompareDialog` take `repoRoot` (center-pane.tsx passes the
  resolved repo). `ReviewNavigator` gets its per-repo data and intents through right-pane.tsx.
  Touched: review-view, review-source-control, commit-picker-menu (+CompareDialog), review-navigator,
  review-file-nav, review-nav-store, center-pane, right-pane, app.tsx, docs.ts, use-range-files,
  hunk-actions, review-note-target, src/review-handoff.

### 3.3 Handoff markdown

- Single repo, or narrowed: **byte-identical to today.**
- All repos: `buildHandoffMarkdown` gains an optional `groups` argument. It emits
  `Review notes on N files in M repos (<sourceLabel>):`, then `## <name>` per repo and
  `### <path>` per file, then today's closing line. `<sourceLabel>` is today's label (`working tree`
  / `staged changes` / …). **Paths are relative to home** for home and nested repos
  (`vendor/proto-schemas/room.proto`), so the agent, whose cwd is home, can open them, and
  **absolute** for attached repos. This deliberately differs from the navigator title (§2.5):
  that one is for a human, and this one has to resolve from the agent's cwd.
- Pending notes on files not in the list are appended per repo, as today. A repo with pending notes
  but no listed files still gets its section.
- Sent stamping: one `patchNotes(root, {op:'sent', ids})` per contributing repo. Handoff is enabled
  only when every contributing root's notes are loaded.

### 3.4 Producers / consumers

| Data / state | Producer | Consumer | Both in scope? |
|---|---|---|---|
| `repoChanges` | mf-changes (host `sendProject`) | Review groups, navigator, chip hints, discard count | **No.** The producer is mf-changes, whose §3 pins the shape and names Review as a consumer. Review only reads it |
| `ReviewSource.repoRoot` | chip, picker, CompareDialog, app open functions, blame lens, History (mf-changes call site) | ReviewView, loaders, picker, handoff | Yes (S1, S2) |
| Marks / notes | ReviewView per root; editor glyph notes | host stores, agent, glyphs | Yes; formats unchanged (K2) |
| Nav model / view-state memory | ReviewView | ReviewNavigator; ReviewView on remount | Yes; both change to absolute keys together (in-memory only) |
| Git intents with `repoRoot(s)` | navigator rows and kebab, action bar | app `onGitAction` / `runGitFanOut` → `gitAction` (root validated against `writeRoots()`) | Yes |

## 4. Edge cases & failure modes

| Condition | Expected behavior |
|---|---|
| **Same relative path in two repos** | Two cards, two rows, independent marks, folds, notes, hits and DOM nodes (K1) |
| 1 repo | Today's UI exactly: no chip, no headers, source unlocked, same handoff bytes |
| 0 repos | Today's "Nothing to review". mf-changes owns the "No git repos" copy |
| ≥2 repos, all clean | `Nothing to review` · `All N repos are clean.` The action bar is hidden, as today |
| `repoChanges` not yet arrived | Today's whole-list loading state; the chip hints read `…` |
| One repo's `git status` fails | It reads as clean (mf-changes D11), so its group is omitted. A per-group error state waits for mf-changes' v1 |
| Commit or range error while narrowed | Today's error + Retry, retried against the source's `repoRoot` |
| **Repo leaves** (root removed, folder missing) while narrowed on working | Falls back to All repos (or single). Live region: `<name> is no longer in this session — showing all repos` |
| Repo leaves while on its commit or range | The commit stays (explicit `repoRoot`, §2.1). A later git failure shows today's error |
| 2 → 1 repos in All repos | Chip and headers vanish, the source unlocks, and the anchor survives (absolute key) |
| 1 → 2 repos while on a commit | S1 keeps the commit on its repo, and the chip shows that repo |
| Commit source without `repoRoot` in an open tab (predates this change; sources are never persisted) | Stamped with `gitRootForSession(active)` the first time the chip becomes visible (S1) |
| Fan-out partial failure | Per-repo toast with the repo name, the remaining repos run, one refresh |
| Double activation of Stage all | Blocked by the awaited `disabled` state (§2.6) |
| Locked source trigger activated | No menu, no state change |
| One repo at 500 open notes | Only that repo's cards refuse |
| 1 000+ files across repos | Card and navigator windowing hold with group items (`review-virtualize` grouped variant) |
| Two windows on the same repos | Marks and notes are already shared through host pushes, and per-root keys stay consistent |
| `.conduit/review-notes.json` in an attached repo | Written there per L7 and hidden from Review by the per-group `NOTES_ARTIFACT_PATH` check (D9) |

## 5. Defaults vs. settings

| Decision | Default | Configurable? | Rationale |
|---|---|---|---|
| Scope on a global open | All repos (working) | No | The one Review button means "everything the agent touched" |
| Chip choice persisted | No (it rides `reviewSource`, which is never persisted) | No | Same as source and scope today |
| Chip visibility | ≥2 repos | No | Single-repo sessions look as today |
| Cross-repo discard / stash / pop | Disabled | No | Irreversible or ambiguous; narrowing is one click |
| Cross-repo stage / unstage all | Fan out | No | Reversible |
| Headers when narrowed | Hidden | No | The chip names the repo; matches the single-repo look |

## 6. Scope slicing

- **MVP (this item):** everything above, plus the e2e in §7.3.
- **Vision:** collapsible or sticky group headers, group jump keys, per-group `···`, and each repo's
  `reviewed/total` in the chip menu.
- **Out of scope:** merged history, cross-repo compare, moving notes out of the repo, the session
  card diffstat (D10), and the preview protocol (L6).

## 7. Acceptance criteria

### 7.1 EARS

1. WHILE the active session has ≥2 present repos, the Review header SHALL render the repo chip before
   the source trigger. WHILE it has <2, no `.review__chip` SHALL exist.
2. WHILE the resolved repo is All repos, the source trigger SHALL have `aria-disabled="true"` and the
   §2.3 title, and activating it SHALL NOT open the picker.
3. WHEN a repo is picked in the chip, only that repo's files SHALL be listed, with no group headers,
   the scope unchanged, and a picker that lists that repo's commits only.
4. WHEN a commit or range is chosen while narrowed, the stored source SHALL carry that `repoRoot`.
   WHEN the scope segment is changed while narrowed, the `repoRoot` SHALL be kept (S2).
5. WHEN `All repos` is picked, the source SHALL be working with no `repoRoot`.
6. WHILE in All repos, the cards and the navigator SHALL show one group per repo with ≥1 listed
   file, in mf-changes' order. Each navigator group SHALL show `reviewed/total`.
7. WHEN a file is marked reviewed, the mark SHALL be stored under its repo root with its relative
   path, and only that group's count and the header total SHALL change.
8. IF two repos change the same relative path, THEN two cards SHALL render with independent
   reviewed state and distinct `data-root`.
9. WHEN `Stage all` is pressed in All repos, every listed repo SHALL have its changes staged, and
   `Discard all changes…`, `Stash` and `Pop` SHALL be disabled with a title.
10. WHEN the handoff runs in All repos with pending notes in ≥2 repos, the text SHALL contain one
    `## <name>` per repo with home-relative (home, nested) or absolute (attached) paths, and each
    repo's notes file SHALL record `sent`.
11. WHILE the session has one repo, Review SHALL be unchanged, including handoff bytes.
12. IF a narrowed working repo leaves the session, THEN Review SHALL fall back to All repos and
    announce it.
13. WHEN a terminal sha link opens a commit in a repo outside `reviewRepos`, THEN Review SHALL show
    that commit (no fallback).
14. WHEN a note glyph is clicked in a nested or attached repo's file, Review SHALL open and land on
    that file's card.

### 7.2 Gherkin (the cross-repo drill-down; the other EARS items are covered 1:1 in §7.3)

```gherkin
Scenario: review everything, then drill into one repo's commit
  Given a session with home repo "rmb", nested "proto" and attached "ci", each with a dirty file
  When I open Review from the Changes tab
  Then the chip reads "All repos" and the source trigger is aria-disabled with the lock title
  And group headers read "rmb Home", "proto Nested", "ci Attached" in that order
  When I pick "proto" in the chip and then "Staged" in the scope segment
  Then only proto's staged files are listed, the chip still reads "proto", and there are no headers
  When I open the source trigger
  Then the picker lists proto's commit subjects and none of rmb's
  When I pick proto's latest commit, then "All repos"
  Then the source is "Working tree" and all three groups are back
```

## 10. Accessibility & i18n (UI)

- Every new control is keyboard-reachable, and every disabled control has a text reason. Tags and
  counts are text, never colour alone.
- Live region (the existing `announce`): chip change → `Reviewing all N repos` / `Reviewing <name>`;
  fan-out done → `Staged changes in N repos`; repo left → the §4 copy.
- Focus: the chip menu returns focus to the chip, and a chip change moves focus to the scroller (K3).
- Contrast: the locked trigger uses the existing disabled treatment from
  interaction-state-vocabulary. No new motion.
- **i18n:** there is no i18n module (measured in review-mode §10). review-view.tsx keeps its inline
  strings; the navigator and the new components use their `STR` objects. Plurals go through
  `src/plural.ts`. Chip and repo names ellipsise at 170px with the full text in `title`, which
  tolerates +30% growth. RTL is not supported app-wide.

## 11. Design tokens (UI)

Existing tokens only, no hex: `--accent` (Home), `--warn` (Nested), `--text-muted` / `--border`

## 12. Assumptions

- A group's `reviewed/total` counts over the currently listed files (scope + filter), the same basis
  as today's header.
- The group display name is `RepoChanges.name`. The full display path goes in `title`.
- mf-changes' `refreshChanges` (with `allRepos`) refreshes every repo, and its display order (home →
  nested by path → attached in roots order) is the order Review uses.
- mf-changes leaves `ReviewNavigator`'s section icons to this item, which drops them in grouped mode
  only (D6).

## 13. Decisions Needed

- **D1 [normal]** mf-changes' `RepoChanges` has no per-repo status: it sends one reply, and a
  failed `git status` reads as clean. Pick: Review shows whole-list loading and has no per-group
  error in this item, following mf-changes' v1 error state when that lands. This item adds
  `GitActionIntent.repoRoots` and `repoRoot` on `git:resolveRange` / `git:rangeDiff` (renderer and
  host), which mf-changes leaves to mf-review.
- **D2 [normal]** Is the chip hidden with one repo? Pick: hidden below 2 present repos, which is
  today's RepoPicker rule.
- **D3 [normal]** Bulk ops across repos. Pick: stage and unstage all fan out; discard, stash and pop
  are disabled in All repos. This protects attached reference repos from an irreversible multi-repo
  discard. The alternative (a fan-out discard behind a confirm that lists each repo) is a small
  change if preferred.
- **D4 [normal]** How is "locked" rendered? Pick: `aria-disabled` + title + sr-only reason, which
  keeps it focusable. `disabled` would hide the reason from keyboard users.
- **D5 [normal]** Handoff paths. Pick: home-relative for home and nested repos, absolute for
  attached, grouped under `## <repo>`. Single-repo output is unchanged.
- **D6 [normal]** Navigator staged/unstaged in grouped mode. Pick: sub-labels only when a group has
  both, and no per-section review icon.
- **D7 [normal]** The `ASSUMED (source-read)` rows in §2.7 were checked by two independent source
  reads, not at runtime. Pick: the builder proves each red-first.
- **D8 [normal]** Group headers when narrowed. Pick: hidden.
- **D9 [high]** L7 says "`.conduit/` in attached folders is ignored" and also "Review notes/marks
  stay keyed per repo root (as today)". Keeping notes per repo writes
  `.conduit/review-notes.json` into attached (possibly reference-only) repos. Pick: follow the
  per-repo clause and write them there. This is a lock-interpretation call for a human. The
  alternative is to store attached repos' notes under home's `.conduit/` keyed by root, which is
  invisible to an agent working in the attached repo.
- **D10 [normal]** The session-card review diffstat is the active repo's git-status count, not
  marks (reviewer check: src/git-info.ts:62, session-card.tsx:237–248), so it will disagree with an
  All repos count. Pick: out of scope here. It is recorded for a follow-up (or for mf-changes, if it
  aggregates per repo).
- **D11 [normal]** Terminal sha links can resolve to a repo outside `reviewRepos`. Pick: keep
  showing the commit (link-cwd behavior) rather than falling back.

No lock in `.autoloop/locked.md` is broken outright. D9 is the one ambiguous reading.
