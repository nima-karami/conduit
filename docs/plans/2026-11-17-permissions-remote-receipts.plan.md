## Architecture / exact contracts
Receiving host owns pending incoming-call context and durable grants. RequestService owns validation, queue lifecycle and answer-id dedupe. Add a synchronous preflight after validation and before queue.answer, not a wait for full tool execution and not an async queue-success shim. Network owner supplies current authenticated inbound principal facts at answer/execution time.

- RequestServiceDeps.onRemotePermissionAnswer(record:RequestRecord,answer:AnswerInput):RemotePermissionPreflightResult is required, synchronous. It runs only for r.remote+r.permission after existing request/identity/source/grantability checks AND explicit validateAnswer(r,input). Invalid answer must never cause grant side effects. Normal agent answers skip this hook and preserve existing behavior.
- RemoteAnswerResult/refuse error union adds policy_unavailable and peer_unreachable (recognized existing ToolErrorCodes); wire shape unchanged. Failure message survives existing server/services.ts→network.requests→host peerRefusalOf→RequestTemplate alert mapping. Do not mislabel save failure invalid_args/not_found.
- applyRemoteAnswer checks existing answerId dedupe first and caches result once as now. Identical wire retransmission never re-persists a grant. Explicit owner Retry uses fresh answerId and can retry after a failed write. Do not change settled answer-id dedupe semantics in this slice.
- Host pendingRemotePermissions Map<requestId,PendingRemotePermission> is populated immediately after createRemotePermission returns, before any await/network turn. Entry binds machineId,handle,tool,resolved targets,absolute deadline,AbortSignal and original policy context. Never reconstruct trusted principal/capabilities from persisted record text.
- askOwner finally removes map entry and abort listener on every created.ended result (answer, timeout, withdrawal, stop/link abort). host.stop clears leftovers after service stop; no retained prepared resources. Preflight cross-checks record identity/tool against entry; missing/stale/cancelled/expired entry refuses without any grant. Explicit now>=deadline guard prevents a late I/O answer racing delayed timer from executing.
- For Deny, preflight verifies pending identity/deadline/cancel state, then succeeds without grants/policy mutation.
- For Allow, obtain CURRENT inbound principal via NetworkPort.inboundPrincipal(machineId,handle):RemoteCaller|null. Rebuild policy input with current link facts and current master switch, original resolved targets/tool/forceAsk. Re-decide current rules; a new floor/deny withdraws with Conduit's reason and returns policy_unavailable, no grant. Do not use peerCapabilitiesOf (opposite direction).
- Calls owner adds Calls.inboundPrincipal(machineId,handle):RemoteCaller|null, deriving BARE_HANDLE + isInboundSsh + live link and cloned current local capabilities. serveCall reuses same construction after preserving specific not-controller/bad-handle validation replies. server/network/index.ts delegates NetworkPort.inboundPrincipal to Calls. This is a shared trusted fact producer for two real callers, not a renderer authorization check.
- Allow+grant uses existing remoteGrantOf/fixed peer×target×until-revoked consent and typed atomic grantsFor. Failure returns policy_unavailable with clear save/scope message and keeps request open for explicit Retry until its original deadline; no queue.answer, no partial grant, no call run. No automatic retry. Success queues answer only after durable grant creation.
- Remove the POST-answer grant creation block in callAsRemote, preventing duplicate grant. Forced asks and prepared alwaysAsk are not grantable; do not offer meaningless future grants for calls required to ask every time.
- Immediately before every p.done/p.run remote execution (including unasked paths), refresh inbound principal+master/rules and commit against that fresh input. Still honor explicit answered Allow once when fresh decision remains Ask; fresh deny/floor refuses. If link/capability/controller role or policy changed since approval, no stale captured permission may run. Existing execution/target/UI readiness checks remain separate and unchanged.
- Owner receipt acknowledges durable consent, not tool completion. Link drop after consent still cancels action via existing served AbortController; no replay. New grant may remain valid consent if action cancelled; peer revoke/floors still dominate it.

### Authoritative queue commit and notification separation (B2)
1. Keep `RequestQueue.answer(id,input,by): QueueAnswerResult` as the public seam, but give it an explicit result guarantee: every returned refusal (and every handled internal preparation failure) is **before** the canonical answer commit; once committed it always returns `{ok:true,record}`. A failed observer is not an answer refusal.
2. In the queue owner, prepare all fallible answer data before mutating the stored record: validate input, obtain timestamp, build the final answered record and its defensive return/notification copies. An exception in this preparation is reported through the owner diagnostic sink and becomes `{ok:false,reason:'not_answerable',message:'the request could not be committed'}` with old state intact. This names a real queue-commit failure without reclassifying grant persistence.
3. Canonical commit is the synchronous publication of the prepared record to the queue store. From that point no injected callbacks or fallible clone/time work may affect the answer outcome. The answer is committed in this process; this does not change the existing asynchronous requests.json persistence contract or pretend that file has been fsynced.
4. Add required `QueueDeps.warn(message:string,data?:unknown):void`, matching the existing `RequestServiceDeps.warn` convention. The diagnostic sink is explicitly non-throwing, like the production logger. Queue terminal notification boundaries catch and report individual callback failures with `{requestId,stage,error}` and continue every remaining notification. Report text: `request notification failed after commit`. No blanket catch around remote apply and no inference from `queue.get()` after an exception.
5. Move timer-map deletion to canonical bookkeeping before calling injected clearTimer. A failed clearTimer is a reported postcommit notification/cleanup failure; a stale timer firing later sees the terminal state and does nothing. Independently notify onEnded and onChanged even when one throws. Prebuilt copies prevent an observer from mutating the returned canonical result.

### Service composite notifications must preserve each stage

The service currently passes one composite onEnded callback, and `changed()` itself loops observers. Guarding only the outer queue callback is insufficient to keep later internal notifications running. In request-service:

- On end, independently perform/report remoteWait settlement, local waits settlement, and late-delivery scheduling in that order. Capture `hadWaiter` before local waits settlement; delete the remoteWait entry before resolve. An exception in one stage must not skip the others.
- In changed(), run internal dirty marking first, then independently perform/report `deps.onChanged()` and **every** mirror listener. Use the same existing `deps.warn` diagnostic sink; no new event bus, queue or observer framework.
- Required production wiring is simply `warn: deps.warn` into createRequestQueue. The only direct queue constructor outside request-service is its unit harness, so add the required spy there. Keep creation/request defaults behavior unchanged except where the shared terminal-notification helper now guarantees remaining observers run.

### Remote preflight metadata and true precommit rollback

Pin these narrow callback shapes in request-service (node-free types where existing deps are declared):

- `RemotePermissionPreflightResult = {ok:true;createdGrantIds:readonly string[]} | Extract<RemoteAnswerResult,{ok:false}>`.
- `onRemotePermissionAnswer(record:RequestRecord,answer:AnswerInput):RemotePermissionPreflightResult`.
- `rollbackRemotePermissionGrants(record:RequestRecord,ids:readonly string[]):PolicyEditResult`.

Deny/Allow-once success returns an empty id list. Allow+grant success returns **only the actual newly-created batch IDs** from the owner grant result. RequestService validates before invoking it. If queue.answer then returns a true precommit refusal, call the rollback dep once for the returned IDs, using the M1 conservative batch-revoke/pending-save owner path. Preserve the queue's actual refusal/message; map true precommit not_answerable to remote policy_unavailable (invalid_answer still maps invalid_args), and report rollback-save error explicitly via existing snapshot/diagnostic path. Never remove prior grants. If queue.answer returns committed success, do not roll back merely because notification errors were reported. Cache the corresponding RemoteAnswerResult under the answerId exactly once.

This is a typed queue-owner guarantee, not a special remote catch that guesses whether state happened to change. Unexpected postcommit notification errors are diagnostic, while the receipt truthfully acknowledges committed durable consent. No full-tool-completion wait is added.
