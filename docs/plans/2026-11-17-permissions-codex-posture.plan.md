# Linked Codex posture implementation plan

Tier FULL: a new owner-only route crosses renderer, host, domain, watcher and filesystem. This revision supersedes the earlier automatic-matcher posture plan. The owner decisions in `permissions-next-contract-decisions.md` are inputs. No native configuration, launch argv, hooks, terminal input or CODEX_HOME changes. The existing scheduler and observed Activity matcher and callbacks remain unchanged. New app controls are a later milestone; this milestone exposes an owner-addressed route and projection, exercised by runtime harness.

## Data flow and contract

Owner window -> `server/mcp/index.ts` resolves connection/window presence -> `host.handleRenderer` validates owner and current live Codex launch -> domain port -> existing watcher checks its already-bound file and exact session_meta UUID -> host pulls sanitized current reading -> addressed owner projection. Watcher append -> domain -> host validates live IDs and active owner link -> addressed projection. The new posture route never logs or exposes the input UUID, bound filename, fingerprint or raw contexts. Existing scheduler diagnostics stay as they are. Posture does not write Activity or persisted fields.

`src/contracts/native-launch.ts` defines `CodexPostureReading = { status:'known'; reportedAt:number; sandbox:'read-only'|'workspace-write'|'danger-full-access'|'external-sandbox'; approval:'on-request'|'on-failure'|'untrusted'|'never' } | { status:'unknown'; reportedAt:number|null }`; timestamps are finite positive parsed UTC milliseconds. `CodexPostureView = { status:'unavailable' } | { status:'linked'; source:'linked-codex-thread'; freshness:'current'|'stale'; reading:CodexPostureReading|null; lastKnown: Extract<CodexPostureReading,{status:'known'}>|null }`. Null reading means no complete context yet; unknown means a complete context with unrecognized or missing leaves or timestamp; stale is a subsequent read failure, retaining the prior facts. No UUID, path or raw producer fields in DTO. Display labels are “Linked Codex thread” and reported time, with no claim of verified live enforcement.

`src/protocol.ts` adds `mcp:linkCodexThread` request `{ requestId:number; sessionId:string; generation:number; threadId:string }` and `mcp:codexPostureQuery` `{ requestId:number; sessionId:string; generation:number }`. Add addressed response `mcp:codexPostureResult` `{ requestId:number; sessionId:string; generation:number; view:CodexPostureView }`; refusal returns unavailable, with no diagnostic containing ID/path. Add addressed `mcp:codexPostureChanged` `{ sessionId:string; generation:number; view:CodexPostureView }`. No IDs except selected Conduit session ID/generation are emitted. Bound requestId and sessionId using existing protocol conventions; reject invalid canonical lowercase UUID `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`, no normalization. Do not echo input. The handler receives the presence-resolved sender from `server/mcp/index.ts`; require sender != NO_OWNER_WINDOW, `ownerWindowOf(sessionId) === sender`, window ready, an existing local session and an actual live terminal with requested generation and native Codex launch evidence matching generation and launchId. Repeat these checks after every await before committing or returning the linked view. Query returns unavailable to any non-owner, stale generation, missing live terminal or unsupported binding. Updates route to the current owner only; recheck ownership at send, and query supplies the state to a newly current owner. Never add it to `uiState()` / broadcast `mcp:state`.

 `src/contracts/server-ports.ts` adds a `codexPosture` property to existing DomainPort. Its synchronous methods are `link(sessionId, ids, threadId): boolean` and `get(sessionId, ids): CodexPostureUpdate|null`. Implement in the existing domain owner and its full fixtures. Updates use the existing ObservedPort with one new `{postureChanged: LaunchIds}` variant. The host branch handles that before Activity processing and pulls only the current validated domain view. Define `CodexPostureUpdate = { freshness:'current'|'stale'; reading:CodexPostureReading|null; lastKnown:KnownCodexPosture|null }` and the known branch alias in native-launch. The watcher alone owns the one explicit per-session association. The host never stores a second link or reading. Query and notifications recheck exact live generation and launch ID and use actual current owner and readiness. Replies and change notifications carry the generation; stale UI updates can be dropped by generation. An exit notification can clear the matching view to unavailable. A linked view with null reading remains pending until the same stream publishes its first complete context. Retirement/replacement/removal drops the group. Controller restart creates an empty watcher. Preserve same-controller reconnect only while both live IDs match. Never place posture in MCP's general snapshot.

`server/domain/codex-rollout-watch.ts`: keep existing matching, `onBound`, scheduler signals, action behavior and disk-read scheduling. Extend `track(sessionId:string, s:{cwd:string; launchAt:number; ids:LaunchIds}):void`, capture immutable IDs and add constant-size private `{reading,lastKnown,freshness}` to each tracked object. Add synchronous `linkPosture(sessionId:string, ids:LaunchIds, threadId:string): boolean`, `getPosture(sessionId:string, ids:LaunchIds): CodexPostureUpdate|null`, `unlinkPosture(sessionId:string, ids:LaunchIds):void`, and dependency `onPosture(sessionId:string, ids:LaunchIds):void`. `linkPosture` accepts only the same currently tracked object, exact IDs, an already-bound file whose parsed `session_meta.id` exactly equals the canonical owner UUID and is not a subthread, and a verified current file identity from a successful existing `readBound` operation. No initial scan or independent offset. If initial read has not established file identity, return unavailable; a successful read with no complete context may link pending. Never select a competing file, change `boundFile`, or create a second matcher. Same-cwd competition bound to the wrong file refuses the owner link; ambiguous bind remains unavailable. Historical/adopted controller launches have no tracked object and cannot link.

`server/domain/codex-rollout-fs.ts`: extend the existing `readFrom(p:string, offset:number)` result to `{data:string; size:number; identity:{dev:number; ino:number; fileSize:number}|null}`. The identity comes from `fstat` on the same open handle that returned the bytes, after checking it is a regular file; reject zero/unreliable inode for posture. Preserve exactly the existing scheduler data/size behavior. The existing first-line read supplies parsed metadata; where a `readBound` starts at offset zero, parse its first complete line again and require the same ID before making identity eligible. For later reads require the same dev+ino and `fileSize >=` the previous consumed offset, and check the tracked object, bound path and IDs after await. When identity changes or size shrinks, invalidate posture and require a new owner link after a fresh valid binding; never alter scheduler offset or matcher to accommodate posture. A read error marks linked posture stale, retaining facts; only a later same-file successful supported context restores current. Null/unreliable identity is unavailable. This proves continuity of reads from a same-handle file, not that a terminal itself authored the file; owner linkage remains explicit.

`src/codex-rollout.ts` adds `rolloutPosture(line:string): CodexPostureReading|null`: only `type:'turn_context'` produces a reading; validate timestamp and enum leaves from the actual documented record shape, whitelist only these fields, and unknown on missing/invalid leaves. In existing `readBound`, privately fold every complete line in file order on every current tracked-object read, including initial replay and append, whether linked or not. `reducePosture(previous, reading)` retains latest reading and replaces lastKnown only on known; apply every row, not just latest. Emit at most once per batch to an active link, including known->unknown in the same batch. Existing `LineSplitter`, offset and readAgain serialization are the only stream; a link during an in-flight read sees the previous safe state and the completion publishes the new state exactly once. Ignore invalid JSON and non-context lines. Never forward raw fields. Guard object, file identity and IDs before each callback. Do not create another filesystem reader, scan, buffer of historical records, or hidden user-content state.
