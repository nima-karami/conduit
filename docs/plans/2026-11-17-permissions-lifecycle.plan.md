# Permission lifecycle owner producers — implementation plan

**Spec:** `docs/specs/2026-11-14-policy-and-permissions.md` §§4.3–4.7, 5.1, 11–12; root decisions `.autoloop/evidence/permissions-next-contract-decisions.md`. **Tier:** FULL: owner authority, persistence, and IPC seams. This producer-only plan received independent architecture approval, including the paged owner view and commit ordering; renderer components and styling belong to the later renderer plan.

## Architecture and data flow

The request queue retains canonical records, call-flow owns live waits and their window IDs, policy-service owns restrictive state and durable grant edits. A per-window owner query returns a bounded, sanitized projection; the global `mcp:state` and generic `RequestView` remain unchanged. Grant and denial commands use the existing owner bridge, never renderer-provided principal or snapshots.

```text
owner query + sender window -> request-service canonical queue
  -> call-flow pending ownership / host principalOf + ownerWindowOf -> addressed projection reply
owner answer -> request-service validation -> call-flow wait -> synchronous policy save -> settlement/receipt
owner lifecycle IPC -> host current bindings -> policy-service CAS -> atomic files -> addressed receipt
```

## Locked decisions

- Remote mirror continues its current approved `peer × target × until-revoked` grant bit and remote revoke; no new remote lifecycle, wire shape, or local identity inference.
- Extend live finite expiry by exactly `max(now, expiresAt) + 3_600_000`; Renew expired original duration using same ID, typed bindings and policy token, with live session/anchor/peer identity. Session-end requires original live anchor, finite renews from now, until-revoked has no expiry. Revoked/suspended cannot renew. Use existing session registry and current peer identity state; a known peer alone is insufficient. Reject unknown, revoked, incompatible or identity-changed peers; if current identity status is unavailable fail closed.
- New grants count real successful policy consumption from zero. Move grant touch/count after any failing override persistence in `commit`; ordinary checking, rejected commit and dry-run never advance usage. Saturate at `Number.MAX_SAFE_INTEGER`. Legacy grants retain absent count and expose last use. Touching use/lastUsedAt never changes the lifecycle CAS revision. Optional `lastConsentedAt` is updated on extend/renew, not `lastUsedAt`; session-end idle decay uses max(createdAt, lastUsedAt, lastConsentedAt), never decay until-revoked.
- Opaque Undo is memory-only, single use, issued only after durable successful revoke, valid strictly before five seconds. It binds the post-revoke grant lifecycle revision, the post-revoke global authority epoch, current policy edit token, exact previous state and original typed bindings. Reject after any authority/lifecycle mutation, expiry, session/peer invalidity, or edit-token change. Suspended grants restore suspended or refuse; never activate them. Failed conservative revocation may remain tightened in memory and cannot mint a receipt.
- Session denial is separate from positive grants and assignments; no native selection is materialized or changed. It precedes grants at explicit-deny precedence, allows the existing eligible exact-target one-use override, and sits below floors. Scope is local principal session + tool; session removal cleans it up. Save before resolving the same pending request. A request-id key makes retry idempotent.
- Migration acknowledgement records only actual `migratedFrom`/offered-session provenance; no inferred historic baseline, no remigration of existing v1/v2. Notice is available only where nondefault provenance exists. Review does not acknowledge. Changes to current on-screen settings retain existing CAS/native-consent rules.

### Protective policy format and marker — proposal for critic

Bump the registered `conduit-mcp/policy.json` and `conduit-mcp/policy.last-good.json` formats from 2 to 3 in `src/contracts/session-identity.ts`. `PolicyFile.version` accepts 1, 2, 3; parse v1/v2 as empty denials and absent acknowledgement, retain unknown fields; serialize v3 after a denial is introduced, and continue v3 on all subsequent saves, even after last denial ends. Do not remigrate. Marker format is exactly `{ "version": 3, "kind": "recovery-unavailable" }`, recognized only by a new `parsePolicyBackup(text)` discriminated union: `{ kind:'policy'; file: PolicyFile } | { kind:'recovery-unavailable' } | { kind:'bad'; reason:'corrupt'|'newer' }`. It is never a valid primary `PolicyFile`. Old readers see version 3 and reject it as newer; new readers explicitly treat marker as unavailable, read-only Observer fail-closed if primary is missing/unreadable, without trying legacy migration.

Before every new durable session-denial commit, including a second denial when the primary and backup already contain v3 denials, synchronously atomically write marker to last-good using `PolicyIo.writeSync`; if marker fails, return `save-failed` with request open and leave the primary/active authority unchanged. Then write v3 candidate primary; if primary fails retain the marker, return error, retain prior in-memory state and actionable wait. Once primary commits, publish it in memory, then write the actual v3 snapshot to last-good via existing backup flow. Failure of final backup leaves marker and produces existing backup warning, while primary success remains success. While v3 is active, all regular primary writes and backup refreshes retain v3; a successful later backup replaces marker with a valid v3 snapshot. A crash before marker leaves original state and no acknowledgement; after marker/before primary leaves old primary authoritative but no fallback; after primary/before backup leaves v3 primary authoritative and restrictive unavailable fallback; after backup leaves two v3 copies. Primary missing/corrupt + marker never loads old fallback or migrates. A v3 primary plus v3 backup forces older readers to fail closed even after primary loss. Marker operation is serialized with all policy saves, so a concurrent save cannot overwrite it with an older snapshot between marker and primary commit. No general transaction framework.

**Critic must challenge:** recovery when a pre-existing v2 primary is valid and the marker remains after a failed v3 write; this represents no acknowledged denial, so the valid v2 primary may load. Verify old binaries' actual newer-primary + newer-last-good path rejects both rather than recovering a stale snapshot. This proposal guarantees process-crash ordering only; it makes no power-loss durability claim. Inspect `atomicWriteFileSync` and test the ordering, without expanding that guarantee.

### Owner projection and answer

Add `OwnerPermissionView` in `src/conduit-mcp/request-types.ts`: `{ id: string; sessionId: string; requester: string; title: string; tool: ToolName; why: string; state: RequestState; createdAt: string; expiresAt: string | null; endedAt: string | null; withdrawReason: string | null; grantable: boolean; answerable: boolean; choices: GrantChoice[] }`. Sanitize title/why/requester with existing request bounds; exclude body, args, raw targets and principal. Use the queue’s existing `ENDED_IN_UI` retention for this view, after filtering for the current owner. The per-caller wait limit does not bound open rows across all callers. Both tabs use addressed windows of at most 50 rows without imposing a new admission cap or silently dropping actionable requests. Open order is ascending `(createdAt, id)`; closed is descending `(endedAt, id)`. Use an exclusive cursor of bounded validated ISO time and request ID, and return `nextCursor` only for actual overflow. Filter canonical rows by current owner before paging; generic request or remote APIs stay unchanged. Existing live card remains actionable independently of the owner list page. Add `RequestService.ownerPermissions(): RequestRecord[]` returning only local permission rows (`kind === 'permission'`, `remote == null`, non-null session); it is internal host-only and returns defensive copies. No agent or remote API receives it.

Add `CallFlow.ownsPermissionWait(requestId: string, windowId: number): boolean`, backed by `waits.pending()` ID/window match and excluding `NO_OWNER_WINDOW`; `CallFlow.answerPermission` retains its existing final ownership check. Add owner query `{ type:'mcp:ownerPermissions:get'; requestId:number; state:'open'|'closed'; cursor?:OwnerPermissionCursor }` and reply `{ type:'mcp:ownerPermissions'; requestId:number; page:OwnerPermissionPage }`. Define `OwnerPermissionCursor = { at:string; id:string }` and `OwnerPermissionPage = { permissions:OwnerPermissionView[]; nextCursor:OwnerPermissionCursor|null }` in request-types. `host.ts` obtains `senderId` from existing authenticated bridge and replies only to sender. For each canonical row: live open row belongs only to the exact pending wait window; expired row belongs only if `deps.ownerWindowOf(sessionId) === senderId`, `deps.windowReady(senderId)`, `principalOf(sessionId) !== null`, `lateGrant === null` and grantable. Never project to an unrelated window. For valid principal enumerate `GRANT_WHO_KINDS × GRANT_CHOICE_ON × GRANT_FORS`; retain choices only where `grantWhoFor` and `grantTargetsFor` resolve all actual targets and session-end has a live local anchor; forced asks have no choices. `answerable` is live ownership for open, eligible late grant for expired. Closed non-expired rows project only to current ready source owner, but are not answerable. Apply the same current-owner and principal checks in `onPermissionAnswer` before the existing late-grant route; the current code only checks a non-null window. Query is refetched by renderer after `mcp:ask`, `mcp:askClosed`, and state changes and on mount/window ownership change; no raw data broadcast. Host always revalidates at answer time.

Extend `PermissionAnswer` with `{ outcome:'denied'; scope:'session'; reason?:string }`, preserving ordinary denies and existing grant answer. Update `request-args.ts` validation/conversion so scope is not discarded; reject it for remote mirrors and closed rows. Add to `CallFlowDeps` a synchronous `saveSessionDenial(requestId: string, sessionId: string, tool: ToolName, beforeNotify: () => void): PolicyEditResult`; execute it inside `CallFlow.answerPermission`, after exact wait/window check, without an intervening await. Recheck canonical open state and current principal through the host callback. Add a narrow owner-only policy-service save seam that invokes `beforeNotify` synchronously exactly once after the primary write succeeds, the in-memory denial is installed and final backup handling has finished, but before `deps.onChanged` or any synchronous recheck can cancel the wait. Install the existing async settlement receipt before releasing the wait. The callback must settle that exact wait with `waits.answer` and send its close notification; an unexpected false result is an invariant failure, never reported as success. Complete the outer committed snapshot and its last-good write before calling the exact settlement callback. Suppress the inner backup warning callback on this path, and publish normal policy notifications and retry scheduling afterward in a finally block. This prevents re-entry from cancelling a later failed conservative save or writing that failed in-memory state to last-good. Do not introduce a general transaction framework. If the marker or primary save fails, never invoke `beforeNotify`, return typed `not_answerable` with visible message and retain the live wait and card. As the entire section is synchronous, timer and competing answers cannot interleave; canonical queue settlement after the exact wait is released remains asynchronous. If process crashes between save and settlement, denial persists; same request ID retry is idempotent, expired/closed requests cannot add a second restriction. A subsequent cancellation cannot roll back the restriction. Test callback exceptions as explicit failure, never swallow them.

### Owner lifecycle and acknowledgement IPC

In policy types define `GrantLifecycleResult = { ok:true; undoToken?:string } | { ok:false; error:PolicyEditError; applied?:'tightening' }`. `PolicyService` adds `extendGrant(id:string, revision:number, expectedToken:string): GrantLifecycleResult`, `renewGrant(id:string, revision:number, expectedToken:string): GrantLifecycleResult`, `revokeGrantWithUndo(id:string, revision:number, expectedToken:string): GrantLifecycleResult`, `undoGrantRevoke(token:string): GrantLifecycleResult`, `revokeSessionDenial(id:string, expectedToken:string): PolicyEditResult`, `acknowledgeMigration(expectedToken:string): PolicyEditResult`. Allocate receipt only after successful durable candidate save; use host crypto ID injection. Revalidate all typed bindings and `expectedToken` for authority-changing commands at commit. Increment persisted lifecycleRevision for revoke/expiry/suspend/renew/extend/restore and peer/session lifecycle transitions; never for use. Maintain an owner-memory global authority epoch, rotating after every successful or conservatively applied policy, denial, or grant lifecycle mutation, including changes to another grant and transitions on current typed peer eligibility, and before a receipt for that mutation is issued; ordinary use/count/lastUsedAt ticks never rotate it. Receipt compares the specific persisted grant revision, global authority epoch and policy token, and checks original finite expiry and live bindings before restoring. Retry/backup failures preserve existing `applied:'tightening'` semantics.

Add typed numeric request/reply variants in `src/protocol.ts`: `mcp:grantLifecycle` with discriminated operation (`extend`/`renew`/`revoke` and id/revision/expectedToken, or `undo` and token), `mcp:grantLifecycleResult`; `mcp:revokeSessionDenial`, `mcp:acknowledgeMigration` using existing `mcp:policyEditResult`. Validate at `src/conduit-mcp/host.ts`, dispatch through `electron/main.ts`, expose corresponding Promise-returning methods and `getOwnerPermissions(state, cursor?): Promise<OwnerPermissionPage | null>` in `webview/use-conduit-mcp.ts`; unsupported/fake bridge returns null or a typed failure, never success. Existing `mcp:revokeGrant` remote route remains unchanged. Owner lifecycle commands have no machine field and cannot target a remote machine's display-only rows.
